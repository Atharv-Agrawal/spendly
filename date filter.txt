     transactions table, summary stats, and category breakdown to a chosen
     time window. The filter is submitted as a GET form with `from` and
     `to` query parameters. When no dates are provided the page behaves
     exactly as before (all-time view). This is the first interactive
     data-exploration feature on the profile page.

  ---
  Security Findings

  [Medium] Date inputs passed to SQL without format validation
  database/queries.py — all three query functions

  Queries are correctly parameterized (no injection risk), but from_date and
  to_date are never validated as actual dates before reaching the DB. Non-date
  strings like "9999-99-99" or a 5,000-character value produce nonsensical
  results and get echoed back into the template. Fix: add a regex guard in
  app.py before any query call:

  DATE_RE = re.compile(r"^\d{4}-\d{2}-\d{2}$")
  if from_date and not DATE_RE.match(from_date): from_date = ""
  if to_date and not DATE_RE.match(to_date):     to_date = ""

  [Medium] Unvalidated preset value reflected into template
  app.py line 145

  preset is passed straight from the query string into the template with no
  allowlist check. Jinja2 auto-escaping protects against XSS in {{ }} contexts
  today, but the value is also adjacent to a <script> block on the same page — a
  risky pattern to let grow. Fix: restrict to known values:

  VALID_PRESETS = {"month", "3months", "6months"}
  if preset not in VALID_PRESETS:
      preset = ""

  ---
  Quality Findings

  [CHANGES REQUESTED] Query duplication across three functions
  database/queries.py

  All three functions repeat the same if from_date and to_date: ... else: ...
  branching pattern. A small helper eliminates the duplication:

  def _date_filter(from_date, to_date):
      if from_date and to_date:
          return "AND date BETWEEN ? AND ?", (from_date, to_date)
      return "", ()

  Each query then becomes one clean path using (user_id, *params, ...).

  [APPROVED WITH SUGGESTIONS] Inconsistent keyword argument style in app.py
  app.py line 153 — get_recent_transactions uses from_date=, the other two calls

  app.py line 145 — covered by the security fix above; same change resolves
  this.
